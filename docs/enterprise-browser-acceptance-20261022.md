# 企業版瀏覽器驗收與對話介面

日期：2026-10-22。使用本機 Streamlit 1.51、Chrome 與 agent-browser 操作真正的網頁；不是以 AppTest 代替選檔。全部帳號、制度、上傳資料均為虛構。啟動環境為 `RAG_PROVIDER=extractive`、`RAG_RETRIEVAL=bm25`、空 `OPENAI_API_KEY` 與空 Reranker 路徑；沒有執行付費 API。

## 角色與流程結果

| 情境 | 實際結果 | 驗證方式 |
|---|---|---|
| 未登入 | 只有登入與虛構展示提示，沒有制度內文 | 瀏覽器 |
| 員工問補打卡 | 一般請假／出勤來源，沒有管理分頁 | 瀏覽器；使用者另確認已看到離線來源摘錄 |
| 主管問交接 | 回答包含主管確認指引，未包含人資 SOP | 瀏覽器；來源完整矩陣另由 AppTest 驗證 |
| 人資問制度疑義 | 回答包含人資 SOP | 瀏覽器 |
| 人資維護能力 | 指定人資有維護管理；一般人資沒有 | 兩個人資帳號分別登入 |
| 登出換帳號 | 前一位的問題與答案不殘留 | 瀏覽器及 AppTest |
| 草稿隔離 | 上傳檔即使宣告 published，匯入後仍為 draft；員工來源沒有它，草稿撤回停用 | 人資、員工兩個分頁 |
| 發布 | 人資另行發布後，員工查得到新制度與引用 | 人資、員工兩個分頁 |
| 撤回 | 人資撤回後，員工再次操作舊答案會收到變更提示，完成重繪後舊答案消失 | 瀏覽器；後續對話版另有舊輪撤回 AppTest |

這是工程操作驗收，不是代表性員工、主管與人資的效率研究。使用者目前只明確確認員工查詢結果；不把工具代操作列為使用者親自驗收主管與人資。

本次選檔使用瀏覽器的實際 file input；沒有宣稱另外驗證作業系統選檔對話框或拖放手勢。上傳元件與應用程式驗證的是同一批實際檔案。

### 驗收發現與修正

- 原生上傳元件顯示傳輸上限 10 MB，企業應用實際檔案上限為 1 MiB。先試降低傳輸上限到 1 MB，但剛好 1 MiB 的檔案會因 multipart 封裝額外占用空間出現 `AxiosError: Network Error`。最終保留原傳輸餘裕，不修改原版 `.streamlit/config.toml`；企業入口隱藏原生上限說明，明確顯示 1 MiB 與 bytes。應用層大小檢查保持不變，邊界重測通過。不要用 `--server.maxUploadSize=1` 啟動本版。
- 空檔錯誤原先顯示 2 MB，容易與介面上限混淆；改為「請提供包含制度資料的有效 JSONL；內容不可為空白或超過長度限制」，檢查邏輯不變，瀏覽器重測通過。

## 對話介面

依使用者要求將表單改成對話窗：

- 左側為主題、制度適用日期、清除對話及登出；中央保留制度查詢、資料來源、本人紀錄及指定人資的維護管理。
- 問題與回答分別以對話泡泡排列，下方輸入框按 Enter 送出。每輪保留自己的日期、引用與回饋。
- 最近 10 輪只放在本次 Streamlit session 記憶體，不將原始問答寫入資料庫；清除對話保留登入與既有稽核紀錄，登出清除身分與對話。
- 每次重繪先驗證所有舊輪次，失去來源權限的整輪問題與答案都移除；其餘有權讀取的輪次保留。
- 仍是逐題離線檢索，未加入跨輪條件推論。請輸入完整問題，不能把對話泡泡當作已接上雲端模型。

真正瀏覽器已驗證連續兩輪、各輪引用／回饋控制項、清除後仍登入；16 項 AppTest 另涵蓋日期保留、10 輪上限、撤回舊輪、降權、停用、登出與管理。新聊天測試先因缺 chat_input 失敗，實作後通過。全套最後結果：**253 passed in 59.00s**，exit 0。限定範圍程式審查未發現 Critical／Important 問題，建議的側欄文案已修正。
